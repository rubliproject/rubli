# Security fix — the backend write key must not reach the browser (2026-10-02)

## Finding (Fable, 2026-10-01, during the Day 14 audit)
`https://rubli.xyz/` serves `<script>window.__RUBLI_CONFIG__ = { writeKey: "…" }</script>` to every visitor. `frontend/docker-entrypoint.sh` injects `RUBLI_WRITE_KEY` into `index.html` at container start (the placeholder `<!-- __RUBLI_RUNTIME_CONFIG__ -->`, `frontend/index.html:45`), `docker-compose.prod.yml:61` passes the key to the frontend container, and `frontend/src/api/client.ts:216-247` attaches it as `X-Rubli-Key` to every mutation. The backend's only guard on those routes is `require_write_key` (`backend/api/dependencies.py:18-43`). So anyone can PATCH ARIA review statuses, promote vendors to ground truth, review GT updates, review price hypotheses, change investigation cases, list and close user issues, and delete feedback. The key value is never to be written into any file or message (it is being rotated).

The platform already has JWT auth (`/auth/register|login|me`, `AuthContext`, `localStorage.rubli_jwt`, and `client.ts:250-263` attaches `Authorization: Bearer` to every request). Registration is open (33 active accounts on prod; the `users` table is `id, email, password_hash, name, created_at, is_active` — no role column). A signed-in user is therefore "any visitor who registered", not an analyst. `require_user_or_write_key` (`dependencies.py:46-78`) already backs the watchlist/folders routes with "key OR any JWT".

## Design (minimal, no schema change)
1. **Admin = allow-listed email.** New env `RUBLI_ADMIN_EMAILS` (comma-separated, case-insensitive). New dependency `require_admin` in `dependencies.py`: passes when `X-Rubli-Key` equals the server key (the aria-cron container and ops scripts keep working), OR when a valid JWT's `email` is in the allow-list AND that user is `is_active`. Empty allow-list → JWT never passes (key only). Dev mode with no key set → bypass as today. `UserOut` (`routers/auth.py`) gains `is_admin: bool` computed from the same list, returned by register/login/me.
2. **Guards.** `require_write_key` → `require_admin` on: `aria.py:389` (PATCH review), `:453` (promote-gt), `:1086` (gt-updates review), `:1217` (POST /aria/run — the cron's key path still passes), `investigation.py:635, 678, 855, 922`, `analysis.py:1464`, `issues.py:127` (list), `:154` (status), `feedback.py:138` (delete). `feedback.py:76` (submit — used by `RiskFeedbackButton` and `ReportIssueDialog`) → `require_user_or_write_key` (any signed-in user; anonymous → 401). `issues.py:80` (POST create) stays as it is (check its guard; if it is public today it stays public — it already has its own rate limit? read it and say).
3. **The browser never sees a key.** `client.ts`: delete the `window.__RUBLI_CONFIG__` interceptor and the global declaration; keep only a DEV fallback — `const WRITE_KEY = import.meta.env.DEV ? (import.meta.env.VITE_RUBLI_WRITE_KEY as string | undefined) : undefined` — attached as today when present (local ergonomics only); the Bearer interceptor is what carries auth in production. `frontend/docker-entrypoint.sh`: stop injecting — replace the placeholder with an empty string and log "runtime config: none"; `docker-compose.prod.yml:55-62`: remove `RUBLI_WRITE_KEY` from the `frontend` service's `environment` (and the comment that says it is injected); `frontend/Dockerfile:29-34` comments updated; `index.html:45` placeholder may stay (it renders as nothing).
4. **UI gating.** `User` (`lib/auth-api.ts:8-13`) + `AuthContext` gain `is_admin?: boolean`. `RowExpand.tsx` band D (`:249-300`): the four status buttons and "Promote to GT" render only when `useAuth().user?.is_admin`; otherwise the band shows one muted mono line — EN "Analyst controls · sign in with an analyst account" / ES "Controles de analista · inicia sesión con una cuenta de analista" (anonymous and non-admin alike; no link to register). `InvestigationCaseDetail.tsx:547` (promote) and its status-change rail: same gate. `RiskFeedbackButton.tsx` and `ReportIssueDialog.tsx`: when `!user`, the submit control becomes "Sign in to send feedback" / "Inicia sesión para enviar comentarios" linking to `/login` (no 401 after the fact); when signed in, unchanged.
5. **Tests** (`backend/tests/test_auth_guards.py`, new): with `RUBLI_WRITE_KEY=testkey`, `RUBLI_ENV=prod`, `RUBLI_ADMIN_EMAILS=admin@example.com`, `RUBLI_JWT_SECRET=test` (monkeypatched before importing the app, or via the existing conftest pattern — read `conftest.py`): PATCH `/aria/queue/48/review` with no headers → 401; with a JWT for `nobody@example.com` → 401/403; with a JWT for `admin@example.com` (insert the user into the test DB `is_active=1`) → passes the guard (any non-auth status is fine — assert `!= 401/403`); with `X-Rubli-Key: testkey` → passes; POST `/feedback` with no auth → 401, with any JWT → not 401; `/auth/me` returns `is_admin` true/false by the list; GET `/issues` with a non-admin JWT → 401/403.

- "Report an issue" / risk feedback: anonymous → "Sign in to send feedback"; signed-in → submits.
