## Prod data steps (in this order, after the owner's go)

Times are estimates for the 9.7 GB prod DB on the VPS (HDD-class disk, 27 GB free on 11-04).

**0. Disk + backup first (~10 min).** `/var/lib/rubli-db` holds two old full copies (`RUBLI_DEPLOY.pre_aria_20261103.db`, `RUBLI_DEPLOY.pre_dq1_20261102.db`, 9.7 GB each). A backup plus a scratch copy need ~20 GB; with 27 GB free that leaves ~7 GB. Ask the owner to delete `pre_dq1_20261102` (the oldest) before starting. Then a WAL-safe backup of the live DB:
```
ssh root@37.60.232.109 "docker exec rubli-backup-cron sh -c 'sqlite3 /db/RUBLI_DEPLOY.db \".backup /db/RUBLI_DEPLOY.pre_rc4_20261104.db\"' && \
  python3 -c \"import sqlite3; print(sqlite3.connect('file:/var/lib/rubli-db/RUBLI_DEPLOY.pre_rc4_20261104.db?mode=ro',uri=True).execute('PRAGMA quick_check').fetchone())\""
```
(`ok` expected; `sqlite3` is in the backup-cron image, checked 11-04.)

**1. Deploy (~5 min).** Merge `release/rc4` → `main` (owner), then `ssh root@37.60.232.109 "bash /opt/rubli/scripts/deploy-safe.sh"`. Health check, then confirm the live bundle prints `[RUBLI] build 2026-11-04-nov-rc4` (deploy skill «Verification»).

**2. Subcategory chain on a scratch copy + swap (~40–60 min; carried from rc2, still not run).** Never on the live DB. In `rubli-backend`, from `/app`:
```
python3 -c "import sqlite3; s=sqlite3.connect('file:/app/data/RUBLI_DEPLOY.db?mode=ro',uri=True); d=sqlite3.connect('/app/data/scratch_rc4.db'); s.backup(d); d.close()"   # ~10 min
sh scripts/category_precompute_chain.sh /app/data/scratch_rc4.db        # ~30–45 min, ends with CHAIN_DONE
python -m scripts.swap_category_precomputes --live /app/data/RUBLI_DEPLOY.db --scratch /app/data/scratch_rc4.db --suffix 20261104rc4           # dry run: prints row counts
python -m scripts.swap_category_precomputes --live /app/data/RUBLI_DEPLOY.db --scratch /app/data/scratch_rc4.db --suffix 20261104rc4 --apply   # ~1–2 min
```
The script is a **dry run without `--apply`** (the rc2 doc's command line omitted it).
Then the `wal_checkpoint(TRUNCATE)` loop (deploy skill) and `rm /app/data/scratch_rc4.db`. The optional `classify_categories` pass on the scratch copy (rc2 § Prod data steps 1) stays an owner call.

**3. Events feed (~1–3 min).** `python -m scripts.precompute_events --db /app/data/RUBLI_DEPLOY.db`.

**4. `aria_vendor_drivers` on prod (~3–8 min).** Checked read-only on prod 11-04: `contract_features_v10` **exists** (3,240,251 rows, 44 columns) and has every column the script reads (`vendor_cid`, `price_volatility_raw`, `price_ratio_raw`, `vendor_concentration_raw`); `vendor_stats.primary_sector_id` exists; `aria_vendor_drivers` does **not** exist yet. So no `--features-db` is needed:
```
docker exec rubli-backend python -m scripts.precompute_aria_drivers --db /app/data/RUBLI_DEPLOY.db
```
One GROUP BY scan of `contract_features_v10`, built in `aria_vendor_drivers_new` and renamed, so readers never see it empty; it holds the write lock while it runs (readers fine under WAL). Without it the new /aria still works — rows just show no model aspect. Also checked: the escenario endpoint's other inputs are on prod (`aria_queue` 5,753 rows in tiers 1–3, `vendor_year`, `ground_truth_cases.source_*`/`case_origin`, last `aria_runs` 452e17c3 of 11-03); `top_institution_id` is derived in the router, not a column.

The fila and escenario sit in a 1 h in-process cache. If anyone opened /aria between the deploy and this step, the cached copy has no aspects: `docker restart rubli-backend` (30–60 s boot) or wait an hour before warming.

**6. Verify.** Open `/aria` (new page, question headline, sky + list), `/aria?vista=lista`, `/aria?ver=clasico`, and one classic deep link (`/aria?vendor=<id>` → lands on `?ver=clasico`), `/vendors/2873` (new question), `/antes-del-fallo` and `/rastro` (both redirect), `/captura`, `/gasto-a-ciegas`, `/arranque` (rc3 figures vs the fact-check logs). ## Rollback

- **Code:** on the VPS `git reset --hard <previous main head>` + `deploy-safe.sh` (~5 min). Or, for /aria alone, a one-line flip in `App.tsx` `AriaEntry` (default back to `<AriaQueue />`) — the classic page is untouched in rc4.
- **Category swap:** `swap_category_precomputes` backs up each live table as `<table>_backup_20261104rc4` before replacing it; to undo, replace each table's rows from its backup (or restore the step-0 backup).
- **aria_vendor_drivers:** `DROP TABLE aria_vendor_drivers` — the endpoint falls back to no model aspects.
- **events feed:** re-run `precompute_events` from the previous code, or leave it (it only feeds the Portada board).
- **Whole DB:** stop backend, swap in `RUBLI_DEPLOY.pre_rc4_20261104.db` per the deploy skill «Scenario C» (mv, never cp over the live file; remove `-wal`/`-shm`), start.
